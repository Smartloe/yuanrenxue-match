# 第11题 —— 后续可执行步骤（第3轮结束时状态）

## 已确认的硬约束（决定解题方向）

1. **答案只能依赖服务端下发的后缀 S**（每次请求 /match/11 都是新的 16 位 hex，服务端按 session 记住）
   - 依据：`diff` 两次响应只有这一行不同；响应头只下发 sessionid；本地存储里只有百度统计。
2. **控制台打印的随机串 X 不可用**：同一份 HTML 两次运行打印序列完全不同；X 与 S 的 20 组候选派生全部不命中。
   ⇒ 服务端无法预知 X ⇒ 被校验的答案不可能依赖 X。
3. 当前 build 里 `window.secretkey` **从未被读写**（accessor 监听为空），运行期字符串表里也没有它；
   唯一暴露的 `SecretKey` 是**逐次随机**的诱饵（96 位全不稳定）。
4. 盾的 8 项检测 + `checkEnv` 在所有可构造环境下都不触发，但真函数依然不注入；
   一旦挂真 DevTools，盾会清空页面（见 `docs/devtools_console.png`）。

## 三条可执行的下一步

### A. 等人工 F12 输出（最快）
让使用者在真浏览器里按 `docs/console_snippet.js` 跑一遍，回传 `YRX11` 行。
重点看：`secretkey` 是否出现、`match1` 是否被赋值、控制台打印内容是什么。

### B. 枚举 VM 入口工厂的字节码偏移（纯技术，最硬核）
- 载荷里每个暴露入口都是同一个工厂按不同 `FF`（字节码偏移）造出来的包装函数；
- 但载荷每次加载都重新随机化标识符，无法跨实例注入 → 用**运行时改写**（已跑通，见
  `tools/cdp_payload_instrumented.js`）在 eval 前插入代码，把工厂暴露到 `window`；
- 然后遍历偏移区间建实例，用「同输入两次结果是否相同」筛出**确定性**入口 —— 真 secretkey 必然在其中。

### C. 逆向载荷里的字符串表
- 字符串是运行时由 `String.fromCharCode(85 ^ table[i++])` 这类表达式物化的；
- 把物化函数整体暴露出来，就能枚举**未被执行的字符串**（例如真函数/真分支里的名字），
  从而定位到正常分支的字节码入口。
